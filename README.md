# huff-canonical

A spec-canonical **Huffman compression backend** in Rust: deterministic codec
kernel, content-addressed filesystem persistence, and an Axum validation
HTTP API. Designed to be reproducible from a clean checkout with only local,
synthetic data — no production accounts or real business data are involved.

The central constraint is implemented and tested explicitly:

> **When symbols have equal frequency, the code-length tie-break is fixed and
> documented, and every codebook emitted is a canonical code.**

See [`FORMAT.md`](./FORMAT.md) for the authoritative wire specification.

## What is implemented

* **Deterministic canonical Huffman kernel** (`crates/huff-core`)
  * Tie-break: `(weight asc, tree-height asc, node-id asc)`; leaves are numbered
    by symbol value, internals in creation order.
  * Canonical assignment by `(length, symbol)`; max code length 32 bits.
  * **Single-symbol** and **empty input** have their own defined conventions
    (length-0 symbol carried in the block header; empty alphabet block).
  * Decoder validates the code-length set (exact **Kraft inequality** in
    128-bit arithmetic), bitstream termination and zero padding, and the exact
    original length — no over-read past the frame and no unbounded output.
  * **Container**: 32-byte header, per-block frames with CRC-32, a **block
    directory**, a cross-checking footer, and an explicit **version gate** —
    unknown versions are refused (`UNKNOWN_VERSION`), never guessed.
  * A multi-step validation report that records each check's verdict and
    basis; failures are never reported as success.
* **Filesystem persistence** (`crates/huff-store`): content-addressed
  `artifacts/<sha256>.hfc` plus an atomically rewritten `index.json`; writes
  are fully verified before they touch disk. SHA-256 and CRC are implemented
  in-repo (no crypto/CRC crate).
* **Axum service + CLI** (`crates/huff-api`): `encode` / `decode` /
  `validate` endpoints and a `serve|encode|decode|validate` command line.
* **Independent tests** (`crates/huff-it`) and an independent Python
  reference (`tools/gen_golden.py`) — golden vectors are not produced by the
  code under test.

## Repository layout

```
Cargo.toml              workspace + pinned dependency versions
FORMAT.md               authoritative wire format
crates/
  huff-core/            data format + codec kernel (no I/O)
  huff-store/           filesystem adapter (content-addressed store)
  huff-api/             Axum app + `huff` CLI
  huff-it/              independent integration tests
    fixtures/           committed golden vectors generated by Python
tools/gen_golden.py     independent Python encoder + decoder (golden source)
```

## Requirements

* Rust stable (developed/tested on **rustc/cargo 1.98.1**); pinned
  dependencies are resolved from crates.io on first build:
  axum 0.8.4, hyper 1.8.1, tokio 1.48.0, serde 1.0.229,
  serde_json 1.0.148, tracing 0.1.41, tracing-subscriber 0.3.20
  (exact pins in the root `Cargo.toml`).
* Python **3.10+** only needed if you want to regenerate the golden fixtures
  (uses the standard library: `zlib`, `hashlib`, `heapq`, `random`).

## Configuration (environment variables)

| variable          | default          | meaning                          |
|-------------------|------------------|----------------------------------|
| `HUFF_BIND`       | `127.0.0.1:8080` | serve listen address             |
| `HUFF_DATA_DIR`   | `data`           | artifact store root              |
| `HUFF_BLOCK_SIZE` | `65536`          | encoder block input size (≤1 MiB)|
| `HUFF_MAX_BODY`   | `16777216`       | max request body bytes (16 MiB)  |
| `HUFF_LOG_DIR`    | _(unset)_        | if set, per-run logs go here     |

`RUST_LOG` controls tracing levels (default `info`, `huff=debug`).

## Reproduce from a clean directory

```bash
# 1. build
cargo build --release

# 2. (optional) regenerate the independent golden vectors
python3 tools/gen_golden.py

# 3. run every test: unit + independent integration tests
cargo test --release

# 4. CLI roundtrip
head -c 50000 /dev/urandom > /tmp/in.bin        # or any local file
./target/release/huff encode /tmp/in.bin /tmp/in.hfc
./target/release/huff validate /tmp/in.hfc
./target/release/huff decode /tmp/in.hfc /tmp/in.dec
cmp /tmp/in.bin /tmp/in.dec && echo MATCH
```

## HTTP request examples

```bash
HUFF_BIND=127.0.0.1:8080 HUFF_DATA_DIR=./data \
  ./target/release/huff serve

# health
curl -s http://127.0.0.1:8080/healthz

# encode (raw bytes in, container bytes out; empty body is valid)
curl -s -X POST --data-binary @/tmp/in.bin \
  -H 'X-Label: sample' \
  -o /tmp/in.hfc http://127.0.0.1:8080/v1/encode -D -

# decode (verified end-to-end)
curl -s -X POST --data-binary @/tmp/in.hfc \
  -o /tmp/in.dec http://127.0.0.1:8080/v1/decode

# multi-step validation report
curl -s -X POST --data-binary @/tmp/in.hfc \
  http://127.0.0.1:8080/v1/validate | python3 -m json.tool

# persistence: list artifacts, fetch one (decoded)
curl -s http://127.0.0.1:8080/v1/artifacts
curl -s http://127.0.0.1:8080/v1/artifacts/<id> -o /tmp/back.bin
```

Bodies are `application/octet-stream`. Errors return JSON with a stable
`error_code` and a `request_id`, e.g.

```json
{"ok":false,"error_code":"UNKNOWN_VERSION","message":"UNKNOWN_VERSION","request_id":"…"}
```

Status codes: `200` ok · `400` malformed/truncated input ·
`404` unknown artifact · `413` body too large · `422`
unprocessable-but-well-formed object (bad magic/version/flags or invalid
container on store) · `500` local store/IO failure.

## Test strategy (assertions are concrete, not "it runs")

* **Golden vectors from an independent implementation.**
  `tools/gen_golden.py` re-derives the format from `FORMAT.md` with its own
  heap, bit packer, container writer **and decoder** (a prefix-set walker,
  CRC from `zlib`). It self-checks valid vectors and writes
  `crates/huff-it/fixtures/golden.json`.
  Roundtrip corpus: empty, single byte, single-symbol run, all 256 byte
  values, extreme skew (multi-block), seeded random, repetitive text.
  Negative corpus: **oversubscribed code tree**, **truncated codeword**,
  **wrong padding bits**, **unknown version**.
* **Two independent Rust decoders.** Each golden vector is decoded by the
  production table decoder and again by `huff-it::indie` (a binary-trie
  walker with its own CRC). Every negative vector must produce the *exact*
  documented error code in both decoders and in the validation report.
* **Property-style local tests**: the full byte alphabet, extreme skews,
  deterministic xorshift random inputs, and lengths straddling block
  boundaries all round-trip through both decoders.
* **Failure-category tests**: Kraft overflow (two constructions), length > 32,
  truncated codeword, set padding bit, inflated output length (no unbounded
  output), `bits_total` past the body, one-symbol-with-positive-length,
  symbol-count mismatch, bad magic/version/flags, header/directory/block CRC
  tampering, directory gaps, total-length mismatch, truncation cuts, trailing
  bytes, and path-traversal artifact ids.
* **Determinism tests**: hand-derived canonical codes (verified with an
  independent `heapq` simulation), equal-frequency ordering, repeatable
  construction, and byte-level agreement with the Python-generated
  256-symbol fixture.
* **HTTP tests**: in-process Axum server on an ephemeral port driven by a
  dependency-free TCP client — encode/decode/validate/artifact flows, empty
  input, exact error codes and statuses.

Run identifiers (16-hex-char `request_id`/run id) appear in every log line so
outputs correlate to an input or invocation; logs record the format version,
progress steps, and the basis for each pass/fail judgment
(`demo/logs/run-*.log` shows an example).

## CLI exit codes

`0` success · `2` codec/validation failure (error code printed) ·
`1` usage/IO failure.
